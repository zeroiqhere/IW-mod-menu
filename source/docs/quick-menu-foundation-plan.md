# Quick Menu foundation and remaining integration

The preceding spacer checkpoint is sealed at 955 source files and 1,256 distinct
registered cases. This writable wave builds source-backed prerequisites for the
complete Quick Menu. It does not replace the full parity objective or claim that
a displayed catalogue executes a source game callback. Installed files and sealed
checkpoints remain unchanged.

## Required source behavior

Main and Quick controls are separate ordered one-to-three-action tuples. Main
defaults to Aim plus Melee; Quick defaults to Aim plus Secondary Offhand. Each
tuple requires explicitly verified saved action groups. Duplicate actions and
paired offhands reject within a tuple; overlap between families is allowed.
None trims its selected and following slots, only after the required first slot.
Tuple revisions are independent; a separate global admission revision changes
whenever either tuple or Disable Quick Menu changes. Rejection or an empty-slot
no-op cannot partially advance owners or counters.

Closed living-player arbitration gives held Main priority over Quick. Dead Quick
uses fixed Aim plus Jump, independent of configured tuples. Disable Quick Menu
gates both Quick routes. Unknown player life cannot become living or dead.
Source authorization and controls-disabled facts remain explicit. Native aggregate
fresh edges adapt the source held monitor; blocked or context-changing input
consumes its completion without replay. The existing live router remains unchanged
until the entire family has a validated integration.

Quick HUD creation is immediate. Its source nominal input wait is 550 ms, while
visible-ordinal row fades can outlive that wait. An elapsed-clock failure keeps a
drawn HUD visible, cancels its fade and starts a conservative finite input wait.
This recovery is a native adaptation, not proof of BO3 engine clock behavior.

Main and Quick retain separate current pages and parent stacks across close/open.
The source cursor and slider maps are shared by exact page name, with slider
values additionally keyed by row. Parent stacks contain page names, so returning
to a shared page reads its current shared cursor instead of an obsolete saved one.

The Quick catalogue preserves exact source order, action tokens and choices.
Living, dead and unknown life and tri-state host/developer facts stay distinct.
Catalogue membership never grants callback authority. No unavailable entry can
become an engine action merely by selecting it.

## Evidence before live integration

GameIdentity.IsAlive proves process lifetime and PID/start-time stability, not
local player life. The existing teammate reader accepts only slots 1..3 and
rejects unsupported living health states; it does not authenticate engine self or
prove death. The scalar personal health loop can itself modify health. None of
these facts supplies the source Is_Alive predicate or hasMenu authorization.

Live integration still requires a proven local entity/session identity and life
predicate, coherent authority facts, strict family/policy protocol, retained
controller histories, runtime dual-chord routing, exact-key instructions,
controller-to-parser-to-renderer joins, and justified IW mappings for every
gameplay callback. Persistence, action-slot/ignoreme restoration, remaining game
families, maps/quests/super-EE and the unresolved retail fatal remain separate work.

## Regression work

Practical behavioral RED precedes implementation. New pure policy tests cover
normal edits, immutable old owners, unavailable bindings, stale and exhausted
revisions, no-op and rejection paths. Arbitration tests cover priority, explicit
eligibility, saved groups, edge consumption and context reseeding. Presentation
tests cover source catalogue, immutable choices, immediate HUD, independent
timelines, clock faults and retained/shared navigation state.

These foundations are not wired into the current controller, public protocol or
live router in this wave. Existing Main behavior and actual 192-profile/252-image
inventories must remain unchanged. Future integration must change the GUI and
behavior together and remain inactive when required live facts are unknown.

The foundation implementation and isolated regressions now pass. The
[checkpoint audit](quick-menu-foundation-reference-audit.md) records the exact
counts and remaining integration requirements; this plan is not live acceptance.
