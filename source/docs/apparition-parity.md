## Memory and lifetime requirements before expanding actions

- Bind every backend to the original process identity and verified retail executable build. Source RVAs alone do not validate a later executable or another map.
- For players, require slot, bounded matching names/GUID, linked entity/client/server identities, connected/playing state, active map globals and supported health/movement state before and after the operation. A display label never substitutes for that identity.
- Establish a real spawn/session generation or a validated transition guard. Stable name/GUID/pointers and monotonic command time do not by themselves prove the same spawn survived a death/respawn cycle.
- The current self health loop now rejects health 1, including startup and loop transitions, with 48 organized feature checks confirmed, including the constructor-range consistency regression. This scalar guard does not establish every downed/dead/After Life state or the teammate reader's richer identity checks. General revive, Demi-God and all-player operations still need their own validated state/lifetime semantics.
- Read the exact typed span, capture original state immutably, change only owned fields/bits, and verify expected state immediately before and after a write. Separate read/compare/write is not a truly atomic compare-and-swap against the game.
- Never restore stale health, an entire flags word, or old values into a replacement player/session. Changed identity or unknown ownership must lock the affected action and report UNKNOWN/restoration failure.
- Code patches require unique exact executable-region identity, matching original/desired bytes, identical restoration width and exclusive session ownership. Existing patches from another tool are not adoptable without recorded originals.
- Stop requests/features/health loops before restoration and final resource release. Attempt independent cleanup even after one error; failed stopping must prevent release of handles still in use.
- Keep input/render threads free of game feature operations and file IO respectively. Source-style menu interaction must not hide the fact that passive inputs still reach the game.
- Preserve bounded private-session IPC, per-command PID/sequence validation, fresh-generation heartbeat, honest pending/unknown state and hard errors for persistent file restrictions. These are orchestration protections, not gameplay proof.

## Rubber-duck method: prove meaning before wiring a control

For each proposed row, state the following in plain language before implementation:

1. **Actor and target:** Is this host-local UI, self gameplay, one currently selected friend, all current players, or the server? Which observed identity grants the target binding?
2. **Requested effect:** What observable change does the reference handler cause? For example, reserve refill is not clip refill; adding score is not setting cash; ignoring AI is not increasing health.
3. **Entry conditions:** Which map, living/downed state, weapon/equipment, host authority and game generation are supported? What makes the control disabled?
4. **State model:** Is the row an action, toggle, enum choice or bounded numeric slider? What does mixed/pending/UNKNOWN mean? What exact observed result earns ON?
5. **Lifetime and exit:** Which events stop it? What original state can safely be restored, and when would restoration overwrite a legitimate game change or a replacement player?
6. **Proof:** Which pure tests, real isolated IO/resource tests and controlled retail observations distinguish correct behavior from a label changing? Include the negative case and map exit.

Examples:

| Proposed control | Correct meaning | False substitute to reject |
| --- | --- | --- |
| Unlimited Ammo / Reload | Keep that player's reserve available while ordinary reload remains necessary | Lobby-wide NOP patch labeled personal ammo |
| Unlimited Ammo / Continuous | Keep that player's reserve and active clip full on weapon changes/firing | Freezing an unverified scalar across weapon changes |
| God Mode | Prevent supported damage for the selected live identity | Checkbox ON while last write/readback failed |
| Demi-God | Reference damage feedback without real damage | Unproven health floor or reusing Godmode label |
| Revive | Complete the actual downed-to-active IW workflow | Writing 100/10000 into downed health |
| Modify Score | Apply chosen delta; zero clears score | Write an absolute fixed cash address |
| No Target While In Menu | Temporarily change validated AI targeting and restore ownership on close | Renderer hides/dims the menu |
| Message Menu | Deliver selected message through a validated intended channel | Showing a local diagnostic log |
