# Quick opening-control settings integration

The preceding foundation is sealed at 982 source files and 1,301 registered
logical cases. This isolated wave connects its policies to the actual settings
controller, GUI, wire parser, command capture and renderer identity checks.
Actual Quick opening, navigation and game callbacks remain required later work.

## Ownership and source behavior

An active immutable pair is the only policy owner when both saved defaults are
verified. Otherwise the existing Main-only owner remains active. Main and Quick
tuple revisions are independent; pair revision changes only for actual tuple or
Disable Quick Menu changes. An actual applied editor target or slot change
invalidates navigation action context, including Main-only fallback. Same target
has no redraw, same Bind Slot redraws once, and both keep the nominal 250 ms wait.
Every action bool attempt keeps source 180/430 ms refresh, including rejection and
None no-op. Actual policies publish immediately while row values retain their
captured previous family until redraw.

The optional openingPolicies object contains exactly revision, main, quick and
quickDisabled. Each tuple contains exactly revision and actions. The existing
mainOpeningControls mirror is required whenever the pair exists and must be
identical to its Main tuple. Legacy Main-only packets remain accepted. Both
saved-key groups must be verified before an active pair can be used. No raw keys,
player-life facts, hasMenu permission or game callback authority are invented.

Commands capture the pair global revision when supplied, otherwise the legacy
Main revision. All supplied editor captures are checked before normal routing.
The worker also reseeds held Main input on any pair change, even when Main did
not change. Receipt and rendered-source identity retain the complete pair so a
Quick-only change cannot reuse obsolete presentation history.

## Regression sequence

Root context tests recorded a compiled inert-method RED with 388 pass/2 fail and
then 390 pass. The combined controller/GUI RED records 391 pass/17 fail: all nine
new controller cases and seven of nine GUI cases failed; two GUI paths already
worked. One existing unknown-preference case also reproduced an appearance-route
gap for the newly appended policy-owned enum. An earlier controller attempt was
a setup compile error and is excluded from behavioral RED.

Twenty-two additional real-controller profiles check exact independent epochs,
mirror equality, captured rows at 0/179/180/429/430, duplicate rejection, trimming,
disable/re-enable, hidden/closed frames, Main-only fallback and retained same-target opening fade. Native malformed,
private-binding, global input-reseed and presentation-history cases require
matching production parser and CPU-renderer joins before this wave is sealed.
The current joins cover 214 producer profiles; final acceptance and exact counts
are recorded in [the reference audit](quick-controls-reference-audit.md).

## Acceptance limits

The settings GUI must explicitly distinguish configured Quick controls from
unavailable Quick opening. Engine life/self/menu authorization are not supplied
by process lifetime or writable health. No game operations or gameplay writers
are added in this wave. Installed bytes and all prior sealed checkpoints stay
unchanged. The full Apparition parity goal, persistence, engine restoration,
gameplay families, map quests/super EE and unresolved retail fatal remain open.
